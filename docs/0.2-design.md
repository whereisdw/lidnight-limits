# Lidnight Limits 0.2 설계 제안

작성: 2026-10-23 · 상태: **제안(미구현)** · 기준 코드: `Sources/main.swift`(0.1.0) · 작성 환경이 Linux라 어떤 Swift 코드도 빌드·실행하지 못했다.
공수: S ≈ 반나절 이내, M ≈ 1–2일, L ≈ 3일 이상(혼자 작업 기준 추정). "Mac 필수"는 Linux에서 검증할 수 없고 Mac에서만 확인 가능한 단계.

**조사에서 나온 중요한 사실 세 가지**

1. CodexBar는 이미 리셋 카운트다운, "기록된 스냅샷 기반 quota burndown", 세션 알림을 갖고 있다(§6). (a)·(c)는 차별점이 아니라 **동등 기능**이다.
2. Claude Code 문서는 `/usage`에 "plan usage bars"가 있다고 설명하고, 상태줄 JSON에 `rate_limits.five_hour/seven_day`(`used_percentage`, `resets_at` 에포크)를 제공한다고 적는다. 0.1이 파싱하는 `Current session: N% used · resets …` 텍스트가 **현행 CLI 출력과 같은지 확인하지 못했다**. 0단계의 이유다.
3. Claude Code 자체에 "사용 한도 리셋까지 기다렸다 자동 이어 하기"(v2.1.234+)가 있다(§6). (d)의 가치는 Claude 단독이 아니라 Codex·두 도구 통합 쪽에 있다.

## 1. (a) 소진 예측

**목표**: 메뉴에 한 줄 — `이 속도면 22:40에 한도` (리셋 전에 100%에 닿을 때만 표시).

**샘플 저장**
- 위치: `~/Library/Application Support/Lidnight Limits/samples.jsonl`(앱 전용 디렉터리, 파일 권한 0600). 한 줄 = `{"t":<epoch>,"tool":"claude|codex","min":300,"used":12.5,"reset":<epoch|null>}`.
- 저장 내용은 **숫자뿐**: 프롬프트·경로·세션 ID·계정 정보는 저장하지 않는다. 네트워크 호출은 추가하지 않는다(README의 "no network calls of its own" 유지).
- 기록 시점: `refresh`가 새 `Limits`를 얻을 때(Codex 매분 / Claude 10분), 직전 값과 같고 5분 미만이면 건너뜀. 8일(주간 윈도우 + 여유) 지난 줄은 시작 시 정리. 메뉴에 "Clear history" 항목.
- 코드 위치: `AppDelegate.refresh(force:)`의 두 `DispatchQueue.main.async` 블록에서 기록, 계산은 순수 함수 `Forecast.eta(samples:now:)`.

**알고리즘**
1. 같은 `(tool, minutes, resetsAt 에포크)` 샘플만 사용(리셋이 지나면 새 윈도우로 시작).
2. 최근 N=6개(또는 최근 60분) 중 시간 폭 ≥ 10분, 샘플 ≥ 3개일 때만 계산.
3. 최소제곱 기울기 `slope`(%/분). `slope ≤ 0.02`면 예측 없음. `eta = now + (100 − used)/slope`.
4. `eta < resetsAt`일 때만 "이 속도면 HH:MM에 한도"(로컬 시각). 아니면 아무것도 안 보여 준다(거짓 경고보다 침묵).
5. 한계: Claude는 10분 주기라 N=6이 1시간 — 짧은 버스트에 둔감. Codex는 턴이 끝나야 값이 갱신되어 계단형. 결과는 "추정"임을 문구로 명시("이 속도면").

**참고(대안)**: Claude Code 상태줄 JSON의 `rate_limits`는 구조화된 값을 주지만, 사용자의 `statusLine` 설정을 건드려야 하고 세션 중에만 실행된다(출처 §6). 0.2에서는 채택하지 않는다.

**공수 M** (순수 함수 + 저장 + 메뉴 한 줄). Mac 필수: 실제 며칠치 데이터로 예측이 체감과 맞는지. 순수 함수는 Foundation만 쓰면 Linux에서도 컴파일 가능하지만 현 구조(`Sources/main.swift` 한 파일, AppKit import)에서는 분리 작업이 먼저다(`build.sh`·`Tests/run.sh`가 단일 파일을 가정 → 다파일로 바꾸면 둘 다 수정, +S).

## 2. (b) 리셋 시각 표시 형식

현재 `Fmt.line`: `5-hour  18% used · resets in 1h 39m`.

제안(상대 + 절대, 로컬 시각):

```
5-hour   18% used · resets in 1h 39m (6:50 PM)
Weekly   43% used · resets Mon 2:00 AM (in 3d 5h)
```

- 24시간 이내: 상대 우선 + 괄호에 시각. 24시간 이상: 요일+시각 우선 + 괄호에 상대.
- 시각은 `DateFormatter` + `setLocalizedDateFormatFromTemplate("jm")` / `"EEEjm"`로 사용자 로캘의 12/24시간제를 따른다. 메뉴바 제목(`render()`)은 그대로.
- `Fmt.line`은 순수 함수라 케이스 테스트 추가 쉬움(`Tests/run.sh`의 `Fmt.until` 테스트와 같은 방식).
- 리셋 시각이 없는 윈도우(`resetsAt == nil`)는 지금처럼 생략.

**공수 S.** Mac 필수: 한국어/영어 로캘·24시간제에서 실제 메뉴 폭과 표기 확인.

## 3. (c) 한도 임계 알림 (80% / 95%)

- `UserNotifications`(`UNUserNotificationCenter`)로 로컬 알림만 사용(네트워크 없음). 첫 사용 시 권한 요청.
- 중복 방지: `(tool, minutes, resetsAt 에포크, 임계값)`을 `UserDefaults`에 기록해 윈도우당 임계값별 1회. 리셋 후 새 윈도우에서 다시 가능. `Window.current()`가 0으로 떨어지면(리셋됨) 기록 무시.
- 기본값: **꺼짐**(조용한 유틸리티 유지), 메뉴에서 "Notify at 80% / 95%" 토글. 알림 본문: `Claude Code 5-hour 95% · resets in 1h 39m` (예측 있으면 (a) 문구 추가).
- 코드 위치: `AppDelegate.render()` 직후 `Notifier.check(claude:codex:)`.

**공수 M.** Mac 필수: 권한 팝업 흐름, `LSUIElement` 앱의 배너 표시, 공증 빌드에서 권한 유지, 집중 모드 동작. CodexBar도 "optional session quota notifications"를 제공(§6).

## 4. (d) Lidnight 연동 1개 — "이어 하기"

**미확정 사항(중요)**: `lidnight://` URL 스킴의 실제 정의는 이 저장소에 없다. 아래는 **제안 계약**이며 Lidnight 쪽 구현·확정이 선행되어야 한다.

- 감지: `NSWorkspace.shared.urlForApplication(toOpen: URL(string: "lidnight://")!) != nil`이면 설치된 것으로 간주(macOS에서는 별도 쿼리 스킴 선언 불필요).
- 표시 조건: 어떤 윈도우가 ≥ 95%(또는 100%)이고 `resetsAt`이 있을 때만 메뉴에 "리셋 후 이어 하기 → Lidnight" 항목.
- 호출(제안): `lidnight://resume?tool=claude|codex&after=<reset epoch>`. 전달 정보는 도구 이름과 에포크뿐, 경로·프롬프트 없음. 네트워크 없음.
- 겹치는 기능: Claude Code는 한도 리셋 후 중단된 작업을 자동 이어 가는 기능을 이미 제공(§6, v2.1.234+). 따라서 가치는 Codex와 "두 도구 한 흐름"에 있다. 이 기능이 Lidnight 구매 동기가 되는지는 별도로 판단해야 한다.
- 설치 안 된 경우: 지금처럼 `lidnight.app/en/?ref=limits` 링크만(변경 없음).

**공수**: Limits 쪽 S, Lidnight 쪽 M(스킴 핸들러·재개 동작 정의). Mac 필수: Lidnight 설치 상태에서 왕복 테스트, 미설치 폴백 확인.

## 5. (e) Intel 빌드 판단 자료

사실(출처 있는 것만. 아래 Intel 관련 수치·모델 목록은 웹 검색 결과 요약에서 가져왔고 개별 기사 본문은 직접 읽지 못했다 — 인용 전 원문 확인 필요):

- macOS 26 Tahoe가 Intel Mac을 지원하는 마지막 메이저 릴리스이고 이후는 Apple Silicon 전용: <https://sixcolors.com/post/2025/06/macos-tahoe-is-the-last-release-to-support-intel/>, <https://appleinsider.com/articles/25/06/09/macos-tahoe-is-the-last-big-update-for-intel-macs>. Tahoe 지원 Intel 모델은 4종(2019 16" MBP, 2020 13" MBP, 2020 iMac, 2019 Mac Pro): <https://www.phonearena.com/news/apples-macos-tahoe-to-be-final-operating-system-to-work-on-intel-macs_id171173>. (macOS 27이 Apple Silicon 전용이라는 보도: <https://itdaily.com/news/workplace/macos-27-end-for-intel-macs/> — 2026-10-23 기준 확인 필요.)
- Steam 사용자 중 Apple Silicon 비율 약 82%(검색 요약은 "2026년 5월"이라 했으나 아래 windowsreport URL 슬러그는 `may-2025`이고 본문은 403으로 열람하지 못해 **연도 미확정**), Intel 약 20%(2025년 2월 보도): <https://itsfoss.com/news/macos-steam-dip-25/>, <https://windowsreport.com/steamos-slips-down-in-may-2025-as-windows-11-keeps-climbing-valves-survey-reveal/>. **한계**: 게이머 표본, 출처 간 연·월 표기가 엇갈림(위 82%는 2025년 수치일 수도 있음). 공식 Steam 설문 페이지(<https://store.steampowered.com/hwsurvey/>, 2026년 9월 표시)는 macOS 점유율(1.92%)만 보여 주고 Intel/Apple Silicon 구분은 없었다.
- **"macOS 13+에서 Intel 비율"을 직접 보여 주는 신뢰할 만한 공개 통계는 찾지 못했다.** 위 수치는 대용 지표이며, 개발자(Claude Code·Codex 사용자)는 최신 Apple Silicon 쪽으로 더 치우칠 가능성이 높다(추정).
- CodexBar 앱은 macOS 14+를 요구하고 CLI는 `macos-x86_64` 타르볼을 따로 배포(§6). 즉 macOS 13 지원은 Limits의 작은 차별점(현재 `build.sh`가 `-target arm64-apple-macos13`).

**판단**: universal 빌드 비용이 낮다 — `build.sh`에서 `arm64-apple-macos13`·`x86_64-apple-macos13` 두 번 `swiftc` 후 `lipo -create`, 서명·공증 절차는 동일(zip 용량만 증가). 사용자층이 작고 줄어드는 중이므로 **마케팅 포인트가 아니라 "받을 수 있는 사람을 막지 않는" 비용 S의 선택**으로 권장. 단, 지원 부담(Intel 실기 없음)은 `arch -x86_64`(Rosetta) 스모크 테스트까지만 약속한다.

**공수 S.** Mac 필수: 두 아키텍처 빌드, `lipo -info`, `arch -x86_64 … --print`, 공증 통과. Homebrew cask(별도 tap 저장소, 이 PR에서 수정하지 않음)는 리뷰어 보고로는 `homebrew-tap/Casks/lidnight-limits.rb`에 `depends_on arch: :arm64`가 있다고 한다(이 세션에서는 tap 저장소를 읽지 못해 직접 확인하지 못함). universal 빌드를 내면 이 제한을 함께 풀어야 한다.
